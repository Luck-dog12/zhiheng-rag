# DeepSeek 思考模式与自适应检索验证

日期：2026-11-20。此次升级针对两项需求：回答时思考并归纳资料；检索时根据证据缺口自行调整查询或检索路线。前一版本使用非思考控制器和非思考回答，虽能进行有限工具调用，但没有强制证据评估和单路检索选择，因此这两项需求此前尚未完整实现。

## 当前实现

控制器与回答继续共用现有 DeepSeek 配置，实际模型为 `deepseek-flash`。两者默认启用思考，推理强度为 `high`；指代消解继续关闭思考。未新增本地模型、数据库服务或其他框架。

```text
问题 + 最近 6 轮可访问历史
  → DeepSeek 思考：明确问题、选择查询和检索路线
  → 检索 / 核验历史证据
  → assess_evidence：充分 / 部分相关 / 无关 / 冲突
      ├─ 不足且有预算 → 改写、拆分子问题或更换路线 → 再次检索与评估
      └─ 充分或预算耗尽 → 选择相关证据 → DeepSeek 思考后回答并附引用
```

- 默认最多 4 次检索、12 个工具决策步骤、480 秒总时限。充分时提前结束；完全无关时不向回答模型传入无关资料，直接说明资料不足；部分相关或存在冲突时仅回答有依据部分并说明缺口。
- 每次检索或复用证据后，必须先调用 `assess_evidence`。在完成评估前不开放下一次检索或回答；不足且还有检索预算时不开放回答。工具参数、真实分块 ID、状态转换均由服务端校验。
- 各轮证据按 `chunk_id` 累积、去重。最终最多使用 5 个已评估的相关片段，重新校验权限和有效文档版本。模型可以选择互补证据，而非仅保留最后一轮的结果。
- 检索策略是实际执行路径：`hybrid` 同时走稠密和稀疏召回，`dense` 仅走稠密，`sparse` 仅走稀疏；重复的“相同查询 + 相同路线”被拒绝。每次仍保留授权、有效版本、RRF 和 Qwen 重排序。
- 当前 `RETRIEVAL_SPARSE_MODE=bm25`，基于**方案 A 的索引**：Qwen 稠密与 Milvus 内置 BM25。Agent 选择单路检索不代表切换为方案 B。此轮没有重新执行 A/B 对比，也没有为方案 B 补做完整端到端验收。
- 最终回答默认概括结论，说明类问题优先少量步骤，不主动输出长代码或整段原文；用户明确要求代码或详细说明时展开。原始段落和完整来源通过引用面板查看。长度是软性引导，不能保证每次都低于某个字数，也不会为满足字数硬截断答案。
- 隐藏推理只用于同次工具循环的协议回传，不写入会话数据库、不通过 SSE 展示。页面仅显示“评估证据”“第 N 轮 · 语义检索”等操作状态。

DeepSeek 思考工具调用不能直接沿用此前的必选工具模式：适配器改用 `tool_choice=auto`，保留并回传同次工具循环的 `reasoning_content`。模型直接输出自然语言时，只作为协议修复上下文，不能绕过取证与校验直接发布为答案。[DeepSeek 思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)、[工具调用说明](https://api-docs.deepseek.com/guides/tool_calls/)。

思考会使用生成额度；开启思考不等于扩大上下文窗口，也不能自动保证简短或准确。保留回答阶段 **8,192 → 16,384 → 32,768 token** 的有界重试、SSE 草稿替换和未完成任务恢复。引用校验失败或预算耗尽仍明确报错，不能把半成品保存为正式答案。[生成参数说明](https://api-docs.deepseek.com/api/create-chat-completion/)。

## 真实外部服务验证

模型、嵌入、重排序、PostgreSQL 和 Milvus 均使用真实外部服务。以下是针对性单次验证，不是统计意义上的准确率或并发性能基线；字符数包含 Markdown 和 URL。

| 场景 | 观察到的行为 | 答案 / 引用 | 耗时 |
|---|---|---|---|
| 临时 API Key 默认、最短、最长有效期 | 混合检索 → 评估充分 → 回答 60 / 1 / 1800 秒 | 113 字符 / 2 个引用 | 16.91 秒 |
| 首轮错配恢复（受控故障注入） | 第一轮混合召回无关文档 → 评估无关 → 改写查询并切换稠密检索 → 评估充分 → 正确回答 | 146 字符 / 3 个引用 | 17.02 秒 |
| 多要点：临时 Key + Rerank 索引及分数 | 一次混合检索覆盖要点，充分后结束；说明 index 对应原输入位置、分数不宜跨请求比较 | 284 字符 / 3 个引用 | 19.31 秒 |
| 未收录的公司食堂菜单 | 混合 → 稀疏 → 稠密 → 稀疏，四轮评估均无关，达到预算后说明资料不足 | 36 字符 / 无引用 | 34.86 秒 |

复测脚本为 `scripts/verify_adaptive_agent_live.py`，可使用 `concise / mismatch / multi / missing / guide` 参数。它复用既有验收账号创建测试会话，随后直接执行生产 `ChatEngine` 和真实依赖；因此表中结果覆盖实际 Agent 与外部服务，但不能单独视为 HTTP/UI 全链路验证。`mismatch` 仅在首次检索替换为真实但无关的查询，后续操作由真实 DeepSeek 决定；它证明恢复机制，不代表生产中自然发生了此故障。

首次错配测试虽然获得正确答案，但没有显式执行评估，测试断言失败。因此增加了“取证后必须评估”的工具可用性约束，再次执行后通过。保留第一次记录 `mismatch-before-assessment-gate.json`，不把它算作通过。

请求观测只保存模型名、思考开关、生成额度和已回传推理消息数量，不保存隐藏推理内容。已确认控制器和生成请求均开启思考，工具循环存在推理消息回传。

## Edge / HTTP 验证

使用本机 Microsoft Edge 访问最新 `8004` 进程，没有下载 Chrome 或 Chrome CLI。通过实际页面、HTTP API 和 SSE 完成两轮会话：

1. “我应该怎么通过百炼 OpenAI 兼容接口调用模型？请简要指导我。”生成 3 个主要步骤，683 字符、3 个引用，无完整代码块。仍附带一条错误提示，说明简洁性是软性指导而非字数保证。
2. “给一个最小 Python 示例。”正确承接上文，自主检索 Python 调用证据，生成 591 字符、1 个引用的代码回答；未要求用户重新描述主题。
3. 展开第二轮引用，验证文档标题、原始段落 34–38 及示例代码一致，原文件链接包含真实文档版本。浏览器控制台 0 错误、0 警告。

两轮均一次生成结束，`finish_reason=stop`，使用 8,192 token 额度，思考开启。没有为了得到简短答案而截断流或限制显示字数。

原始结果保存在 `output/adaptive-agent-live/`：各场景 JSON、`browser-results.json`。截图位于 `output/playwright/adaptive-agent-followup.png` 和 `output/playwright/adaptive-agent-citation.png`。较早的指导回答 901 / 776 字符记录保留为提示词调整前后观察，最终页面验证以 `browser-results.json` 为准，不据此宣称稳定的缩短比例。
